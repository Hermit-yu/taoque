# Network-VNO-AI 算法文档（ALGORITHM.md）

所有公式均为真实数学，单测可验证（见 `tests/run_tests.sh`）。

## 1. BDP（带宽时延积）

```
BDP(字节) = 带宽(Mbps) × RTT(ms) × 1000 / 8
```

例：1000 Mbps × 100 ms → 12,500,000 字节。BDP 只作为"链路满速时飞行中数据量"的参考，**不直接设为缓冲区上限**（否则空闲时浪费内存，高并发时仍可能不够）。

## 2. 多因素内存预算

缓冲区不能无限大：每条连接都吃内存，盲目放大 → OOM 风险。

```
系数 = 按总内存分级：
  <512MB      → 10%
  <2GB        → 20%
  <8GB        → 30%
  ≥8GB        → 40%

可用字节     = 可用内存 × 系数（下限 16MB 兜底）
每连接预算   = 可用字节 / 预估并发连接数（下限 16KB）
```

预估并发按业务场景：网站 256、高并发 4096、代理 1024、高带宽/高RTT 1024 等。

## 3. 最终 rmem_max 计算（三重约束取最小）

```
rmem_max = min( 2×BDP , 每连接预算 , 硬上限 )
硬上限按内存分级：<512MB→512KB, <2GB→2MB, <8GB→4MB, ≥8GB→16MB
下限 64KB（自动窗口调节需要空间），按 4KB 对齐
```

wmem_max 对称处理。core.rmem_max / core.wmem_max 取同样的值。

**验证**：512MB + 1000Mbps + RTT100 场景，BDP=12.5MB，但每连接预算仅约 200KB → rmem_max 被内存封顶到约 204KB，远小于 2×BDP，证明不会爆内存。

## 4. 三档决策（不只看内存）

```
Level 1（稳定优化）：总内存 < 2GB
Level 2（均衡优化）：2GB ≤ 内存 < 8GB
Level 3（高性能，需实测验证）：内存 ≥ 8GB 且（带宽≥500Mbps 或 RTT≥30ms）
```

8GB 以上也**不盲目升 L3**：仅在高带宽/高 RTT 且数据已实测时才建议 L3。

## 5. 需求1：已合理判定（already_optimal）

同时满足以下条件即判定"参数已合理，不建议修改"：
- 当前 rmem_max ≥ 1.5×BDP
- tcp_moderate_rcvbuf = 1 且 tcp_window_scaling = 1
- 总内存 ≥ 2GB
- RTT < 30ms
- CPU Steal < 5%
- 无连接异常（重传/Listen 溢出在阈值内）

## 6. 需求2：拥塞控制能力门控

```
若内核未注册 BBR（available 列表无 bbr）：不推荐，保持当前（CUBIC 类默认最稳）。
若已注册：
  受限虚拟化（OpenVZ/LXC 共享内核）→ 切换可能不生效，保持当前。
  非受限 且 (RTT≥30 或 带宽≥500Mbps) → 可评估切换 BBR（需单独确认 + 实测验证）。
  低延迟/低带宽 → CUBIC 更稳妥，保持当前。
```

BBR 进入主线内核始于 4.9；模块会读取 `kernel.osrelease` 判断是否具备内核条件，但**绝不因此强制升级内核**。

## 7. qdisc 业务场景建议

- 低延迟（low_latency）→ 建议 fq_codel（控制排队延迟，缓解 bufferbloat）
- 大带宽/高 RTT（high_bandwidth / high_rtt_cross_region）→ 建议 fq（公平排队 + pacing），配合 BBR
- 通用 → 保持当前，必要时可评估 fq_codel

任何 qdisc 切换都要求：备份现有 tc 规则 + 用户单独确认。

## 8. 性能闭环评价（benchmark）

评价**完全基于本机调优前后两次快照的真实对比**，分两层，绝不预设结论：

**① 参数层（脚本调优是否真的改了系统）**
快照在采集时会用 `read_sysctl` 直接读 `/proc/sys` 当前生效值（tcp_rmem/wmem、拥塞控制、窗口缩放、moderate_rcvbuf、core rmem/wmem、default_qdisc）。
若 `safe_config` 写入了配置但并未真正 `sysctl` 重载，`/proc/sys` 仍是旧值 → 参数层无差异，评价会如实反映「参数未生效」，不会把网络波动误归功于调优。

**② 网络层（真实测量变化）**
```
  rtt_delta   = 复测RTT - 基准RTT        （越低越好；改善阈值 ↓5%）
  bw_delta    = 复测带宽 - 基准带宽       （越高越好；改善阈值 ↑5%）
  retrans_delta = 复测重传 - 基准重传     （越少越好）
```

**判定逻辑（严格两层结合）**
```
若 RTT 与带宽两端都无有效测量值 → 数据不足，诚实退出，不假装「不显著」
否则：
  improved = (RTT改善?1:0) + (带宽改善?1:0) + (重传改善?1:0)
  degraded = (RTT退化?1:0) + (带宽退化?1:0)
  参数已变化 且 improved>0 且 degraded==0 → 优化有效，建议保留
  参数未变化 但 improved>0                → 改善可能源于网络自身/未真正生效，提示确认 apply
  参数变化 且 degraded>0 且 improved==0    → 建议回滚
  参数未变化 且 degraded>0                → 退化与调优无关，排查线路
  其余                                      → 变化不显著，建议多轮复测
```

> 单次测量受网络波动影响，结论必须多轮验证；本工具只呈现真实差值，不替你下「一定更好」的结论。

**结论文字的真实性**：上述每一种判定对应的 `verdict` 不是固定套话，而是动态拼装——会嵌入**本次实测的具体数值与方向**，例如退化的真实描述形如：
`未观察到收益且出现退化（生效参数变化：tcp_rmem_max:87380->4194304 拥塞控制:cubic->bbr …）；网络层实测：RTT 50.00→65.00ms (+30.0%, 退化)；带宽 100.00→90.00Mbps (-10.0%, 退化)；重传 10→20 段 (退化)；建议回滚（safe_config --rollback）。`
JSON 同时输出 `net_summary` 字段，供程序直接消费这些具体变化。这样无论何种结论，都是「按实际情况做出真实描述」，而非写死的句式。
> 这一点正对应"评价要基于机器经过脚本调优后的实际变化对比"的硬性要求。
